# Agent Notes

Project map for coding agents. The README is the user-facing document; this file records
the conventions and the environment traps that cost a session when rediscovered.

## Repository layout

- One directory per model under `ml/`, `cv/`, `gen/`, `nlp/`, `graph/`, `rl/`, `selfsup/`.
- `config.yaml` in each model directory is the single source of hyperparameters; `train.py`,
  `eval.py` and the notebook read it.
- Notebooks are generated by `scripts/gen_<model>_notebook.py`; regenerate them instead of
  hand-editing the `.ipynb`.
- CI (`.github/workflows/notebooks.yml`) runs static gates on every push and a CPU smoke
  subset through `scripts/run_notebooks.py`; a notebook is only verified by running it.

## Remotes

`main` is pushed to both `origin` (GitHub) and `hf` (Hugging Face) at the same commit. The
exact commands, including the token helper, are in the README "Remotes" section.

## Environment

- Host: NVIDIA DGX Spark, aarch64, GB10 GPU with 48 SMs and driver 580.178.04.
- Python 3.12 managed by `uv`; `.venv` carries `torch 2.12.1+cu130`.
- `data/` holds Pascal VOC and Oxford-Pet; MNIST/CIFAR-10/CelebA come from the Hugging Face
  cache. `results/` and `runs/` are git-ignored local artifacts.

## GPU access under an agent sandbox

A GPU probe inside a `workspace-write` sandbox can fail while the hardware is healthy:

- `nvidia-smi` → `Failed to initialize NVML: Unknown Error`;
- `torch.cuda.is_available()` → `False` with `CUDA error 304`;
- `open("/dev/nvidia*")` still succeeds.

The sandbox blocks the driver calls, not the driver. Re-run the probe with
`danger-full-access` before diagnosing hardware. Verified 2026-11-16 under full access: GB10,
capability (12, 1), 8K BF16 matmul at 96.0 TFLOP/s, and a BF16 conv forward/backward step.
Kernel `NVRM` assertions in `journalctl -k` are not evidence of a broken GPU either.
